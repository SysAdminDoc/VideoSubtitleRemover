### P1

- [ ] P1 -- RM-161: `Run_VSR_Pro.ps1` throws instead of repairing under Windows PowerShell 5.1 -- it dies in exactly the case it exists to handle
  Category: reliability
  Where: `Run_VSR_Pro.ps1:2,7` and the byte-identical embedded copy generated by `setup.py:781-830`
  Problem: The script sets `$ErrorActionPreference = "Stop"` and then probes the venv with `& ".\venv\Scripts\python.exe" -c "import cv2, PIL, numpy" 1>$null 2>$null`. Under Windows PowerShell 5.1, redirecting a native command's stderr converts its stderr output into error records; with EAP=Stop the first traceback line from the failing import terminates the script with a `NativeCommandError`. So when the venv is broken -- the one situation the launcher's repair branch exists for -- the launcher aborts with a PowerShell error instead of running `setup.py --repair`. The `.bat` launcher handles the same probe correctly via `if errorlevel 1`, so the two shipped launchers diverge precisely on the repair path. Line 22's bare `python -c ...` has the same shape: a terminating `CommandNotFoundException` if `python` is not on PATH, where the `.bat` degrades gracefully.
  Evidence: Reproduced on this machine. `powershell.exe -NoProfile -File` on a script with `$ErrorActionPreference="Stop"` plus `& cmd /c "echo boom 1>&2 & exit 1" 1>$null 2>$null` prints `THREW: RemoteException`; the identical script under `pwsh` 7 prints `NO-THROW exit=1`. Windows' right-click "Run with PowerShell" and the default `powershell.exe` are both 5.1.
  Fix: Wrap the probe in `try/catch` with `$ErrorActionPreference` temporarily set to `Continue`, or invoke through `cmd /c` and inspect `$LASTEXITCODE` without redirecting stderr. Apply the same change to the copy embedded in `setup.py` so regenerated launchers stay identical, and add a test that runs both launchers' probe branch under `powershell.exe`.
  Acceptance: With a deliberately broken venv, `powershell.exe -File Run_VSR_Pro.ps1` reaches the "Runtime setup or repair required" banner and runs the repair rather than terminating.
  Confidence: Verified (reproduced empirically)
  Effort: S

- [ ] P2 -- RM-162: Stopping a batch during the encode/mux stage silently replaces the destination with an audio-less salvage and deletes the resume checkpoint
  Category: correctness
  Where: `backend/_encode_mixin.py:463-491` (`_reencode_or_copy`'s blanket `except Exception` ending in `_salvage_intermediate`), `backend/_encode_mixin.py:664-720` (`_merge_audio`'s `CalledProcessError` retry ladder), `backend/subprocess_policy.py:226-239` (`cancel_check` consulted only at the top of the poll loop), `backend/processor.py:985-998` (`terminate_active_work`), `backend/processor.py:2960-2971` (checkpoint cleanup ordering)
  Problem: Pressing Stop while the final encode/mux ffmpeg is running kills that child. In `run_process` the kill surfaces as a nonzero return from `proc.wait()` -- `cancel_check` is never re-consulted after `wait()` returns -- so the caller sees `CalledProcessError`, indistinguishable from a genuine encoder failure. `_merge_audio` therefore *retries* the merge, and when the ladder bottoms out calls `_reencode_or_copy`, whose fresh ffmpeg immediately trips `cancel_check` and raises `InterruptedError`. That `InterruptedError` is swallowed by `_reencode_or_copy`'s blanket `except Exception` ("FFmpeg re-encode failed; salvaging intermediate"), which salvages the video-without-audio file over the user's destination path and returns success. `process_video` then writes the reproducibility sidecar and calls `cleanup_pause_checkpoint`, **deleting every resume frame**, before finally tripping on the cancel at the closing `_report_progress(1.0)`. Net effect: the item reports "Stopped", the destination file has been silently overwritten with an audio-less salvage, and the resume material needed to continue is gone. A second arm of the same defect: `InterruptedError` is an `OSError` subclass, so the deinterlace path catches it twice (`backend/io.py:963`, then `backend/processor.py:2238-2243` "Deinterlace failed, continuing with original") and a cancelled job keeps decoding until the next progress callback.
  Evidence: Traced GUI Stop through `gui/processing_controller.py:148-150` (`cancel_event.set()` then `_terminate_active_backend_work` -> `remover.terminate_active_work`) into `_run_checked_ffmpeg(cancel_check=self._is_teardown_requested)`. Confirmed `_reencode_or_copy`'s final `except` arm at `_encode_mixin.py:487-491` catches everything and calls `_salvage_intermediate` with no `InterruptedError` re-raise, while `_encode_frame_sequence` does re-raise it. `InterruptedError` is the established cancel contract (`processor.py:2977`, `processing_controller.py:863-871`). Distinct from the 3.32 audit's rejected claim -- termination does happen; the post-termination *classification* is what is wrong.
  Fix: Re-raise `InterruptedError` unconditionally in `_reencode_or_copy`, `_merge_audio`, `_deinterlace_to_temp`, and the deinterlace wrapper; check `self._is_teardown_requested()` before treating a `CalledProcessError` as an encoder failure; and re-check `cancel_check` in `run_process` after `proc.wait()` returns, before raising `CalledProcessError`.
  Acceptance: Stopping a batch during the mux stage leaves the destination file untouched (or absent), preserves the pause checkpoint so Resume works, and reports the item as Stopped without any "salvaging intermediate" log line.
  Confidence: Verified
  Effort: M

- [ ] P2 -- RM-163: The per-frame timing probe silently fails on feature-length videos -- VFR sources get CFR timing and good files can hard-fail as `truncated_decode`
  Category: correctness
  Where: `backend/io.py:580-623` (`_probe_video_frame_timing`), `backend/subprocess_policy.py:20` (`DEFAULT_MAX_OUTPUT_BYTES = 8 MiB`) and `:106-127` (`_BoundedCollector._drain` discards from the **head**), `backend/processor.py:2302-2314` (the `total_frames` correction that depends on the probe)
  Problem: The probe runs `ffprobe -show_frames -of json` through `run_process(capture_output=True)` without overriding `max_output_bytes`. Each frame contributes roughly 70-110 bytes of pretty-printed JSON, so any video past roughly 80k frames (about 45-55 minutes at 24-30 fps) exceeds the 8 MiB cap. `_BoundedCollector` was built for stderr *tails*, so it drops from the front of the buffer -- the JSON document loses its opening, `json.loads` raises, and the probe returns `None` behind a `logger.debug` line. Independently, `-show_frames` decodes the entire stream, so long or 4K sources routinely blow the fixed 120 s timeout for the same silent `None`. Three consequences: long VFR sources are processed on the CFR clock (mistimed matte timestamps, audio seek offsets, SRT cues, audio drift); `total_frames` keeps the decoder's header estimate, and when that estimate overshoots the real count -- common on VFR/MKV -- the decode loop ends early and the job **hard-fails with `truncated_decode`** on a perfectly good file, because the PTS map that would have corrected the count vanished silently; and every long video pays up to 120 s of full-decode probe latency for nothing.
  Evidence: `_BoundedCollector._drain` pops `self._chunks[0]` and trims from the front (`subprocess_policy.py:106-127`) -- head-trim by design. `_probe_video_frame_timing` passes no `max_output_bytes` and a fixed `timeout=120.0`; it is called unconditionally for every file input at `processor.py:2302-2303`. Both failure modes are logged at DEBUG only.
  Fix: Use a compact ffprobe output form (`-of csv`, roughly 20 bytes/frame) or parse the stream incrementally; raise `max_output_bytes` for this specific call; scale the timeout with source duration as the Whisper path already does; and log the CFR fallback at WARNING when the source could be VFR so the degradation is visible.
  Acceptance: A 60-minute test source yields a populated `VideoFrameTiming` (or a WARNING naming the reason); a VFR source whose header frame count overshoots no longer fails with `truncated_decode`.
  Confidence: Verified (mechanism traced; the exact minute threshold is arithmetic, not measured)
  Effort: S-M

- [ ] P2 -- RM-174: The PyTorch LaMa path returns padded-size frames on non-mod-8 resolutions and crashes the job
  Category: correctness
  Where: `backend/inpainters/lama.py:636-641` (full-frame) and `:684-705` (tiled); contrast with the ONNX/DNN crops at `:415`, `:535`, and the batched crop at `:768`
